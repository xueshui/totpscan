# 扫码增强型 TOTP 认证协议 v1

- 规范标识：`TOTPSCAN/v1`
- 状态：草案（Draft），可评审
- 适用范围：在标准 TOTP（RFC 6238）认证器之上，增加“扫码辅助提交 + 绑定地址钉住（注册域名 + 提交路径）”的增强层
- 规范性关键词：本文中的“必须 / 不得”（MUST / MUST NOT）、“应当 / 不应”（SHOULD / SHOULD NOT）、“可以”（MAY）按 RFC 2119 解释

---

## 0. 定位与本规范的边界

本规范只解决一件事：**App 与站点如何对上**——二维码里放哪些字段、App 如何比对、提交发到哪里、请求体长什么样、TOTP 参数如何映射到 RFC 6238。

因此本规范把要求分成两类：

- **A 类｜协议约定（必须）**：二维码字段名 / 类型 / 含义、站点域名比对规则、提交目标与提交格式、TOTP 参数语义。任何一端偏离都会导致两端对不上，属于验收条件。
- **B 类｜实现建议（非验收）**：token 时效与一次性、失败计数、限流、统一错误响应、日志与存储方式、密钥管理、部署形态、防钓鱼的额外提示等。这些属于各接入方自身的安全水位，由接入方自行决定；本规范给出推荐做法，但不作为互操作或验收的通过条件。

> 依据：RFC 6238 只定义基于时间的一次性口令算法，本身不要求一次性消费、失败锁定、重放记录或限流。把这些写成协议强制项，等于把站点安全策略混进互操作标准。

§11 按 A 类 / B 类 / 客户端能力三组列出条目；§9 的测试用例只把 A 类作为验收项，B 类用例标注为“参考”。

## 1. 概述与定位

### 1.1 这套协议是什么

本协议定义了两个二维码、一条提交链路和一组服务端校验规则：

1. **绑定二维码**：由服务端在首次绑定时展示，携带 TOTP 共享密钥 `sec`、站点域名 `dom`、提交路径 `path`。认证器 App 扫码后**不验签**，将 `sec`、`dom`、`path`、`bid` 等写入本地安全存储，并钉住 `dom` 的注册域名、`path` 原值与完整提交地址。
2. **登录二维码**：由登录网页展示，携带短效会话标识 `token` 与一个**仅供比对**的站点域名 `url`。
3. **提交链路**：App 扫码后，用二维码中的 `url` 反查本地所有扫码型账户的钉住域名（§6.2）；无候选则本地终止（零出站）；命中后计算动态码，并**提交到该账户钉住的完整提交地址**（`scheme + dom + path`，绝不使用二维码中的地址），请求体为 `{"code","token"}`。
4. **服务端校验**：校验 `token` 存在、未过期，并（建议）与会话绑定，再以“前一个 / 当前 / 后一个”三个时间窗校验 TOTP。token 一次性、失败计数与限流属于站点实现建议（§8.4、§11），不是协议强制项。

### 1.2 这套协议不是什么（重要）

- **不是“扫码登录”**：本协议不产生、也不传输任何长期会话令牌（session token / bearer token）。二维码里没有任何可直接换取登录态的凭据，唯一的凭据是 App 内部按 RFC 6238 计算出的 6 位动态码，且该动态码只能用于一次性提交。
- **不是 WebAuthn / FIDO2**：不提供基于公钥的设备绑定、origin 强绑定与抗中继的密码学保证，无法达到“抗钓鱼认证器”的等级。见 §10。
- **不是“二维码里带一个登录链接”**：二维码中的地址不参与任何网络请求。它只是“这台服务器是不是我绑定时那台服务器”的比对依据。

### 1.3 与标准 TOTP 的差异

| 维度 | 标准 TOTP | 本协议 |
| --- | --- | --- |
| 动态码输入方式 | 用户手抄/复制到网页 | App 扫码后自动提交 |
| 绑定信息 | 通常只存 secret | secret + 钉住的注册域名 / 提交路径 + 完整提交地址 |
| 防钓鱼手段 | 无（用户可被诱导把码交给钓鱼站） | 地址比对，命中才计算与提交 |
| 凭据生命周期 | 动态码 30s | 动态码 30s + 登录 token 短效（建议 ≤60s） |
| 失败处理 | 由业务自定 | 建议统一错误响应 + 失败作废（非强制，见 §8.4） |

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 绑定（Binding） | 服务端为某账户生成 TOTP 共享密钥，并把“密钥 + 站点域名 + 提交路径”交给 App 钉住的一次性过程 |
| 钉住地址 `dom` / `path` | App 在绑定阶段写入安全存储、后续**唯一**允许提交的站点域名与提交路径，之后不再接受任何来源覆盖 |
| 注册域名 | 由客户端用完整 PSL（ICANN + PRIVATE 段）从 host 推导的可注册后缀 + 下一级标签（如 `example.com`）；服务端不承担该推导 |
| 登录二维码 | 登录页展示的、含 `token` 的二维码 |
| 登录 `token` | 服务端签发的短效会话标识（16 或 24 个 base64url 字符），用于把“这次提交”与“这个浏览器会话”关联起来 |
| 时间窗（window） | TOTP 时间步偏移，取 `-1 / 0 / +1` |
| 会话（session） | 浏览器侧的服务端会话，由 HttpOnly Cookie 承载；`token` 应当与其绑定（实现建议，§8.4） |
| 统一错误响应 | 对所有认证失败返回完全相同的状态码与响应体，不暴露具体失败原因 |

## 3. 威胁模型与信任边界

### 3.1 假设

- 服务端不签发、不校验、也不持有任何绑定签名密钥（v1 无签名）；HTTPS 证书链有效。
- App 的安全存储（iOS Keychain / Android Keystore 或等效机制）未被攻破，设备未被 root/越狱。
- 设备时钟与服务端时钟偏差在 ±1 个时间步（30s）以内。
- 用户会核对绑定二维码的来源与确认页上的 `iss` / `acc` / `dom` / `path`（绑定载荷不签名，首次信任建立完全依赖人在回路）。

### 3.2 防御目标

| 编号 | 威胁 | 防御手段 |
| --- | --- | --- |
| T1 | 钓鱼站展示伪造登录二维码，诱导 App 提交动态码 | 登录二维码 `url` 与钉住的 `dom` 按注册域名比对（§7） |
| T2 | 二维码被替换/篡改，注入攻击者的 secret 或提交地址 | **无密码学防御**：绑定载荷无签名，App 不验签；只能依赖用户核对确认页字段与二维码来源（§5、§10） |
| T3 | App 被诱导把动态码发往攻击者服务器 | App 只向钉住的完整提交地址提交；二维码地址仅用于比对 |
| T4 | 动态码被截获后重放 | 三时间窗 + 时间步重放防护（实现建议） |
| T5 | 暴力枚举 6 位码 | 单 token 失败作废 + 限流（实现建议） |
| T6 | 跨会话盗用 token | token 与服务端会话绑定（实现建议） |
| T7 | 通过错误信息差异做 oracle 探测 | 统一错误响应 + 等价计算路径（实现建议） |

### 3.3 信任边界

```
[服务端] --HTTPS--> [登录网页] --二维码(不可信输入)--> [App] --HTTPS--> [钉住的提交地址]
```

二维码内容一律视为**不可信输入**：绑定二维码无签名、App 也不验签（§5），登录二维码必须完成地址比对（§7）后才能使用。

## 4. 绑定流程与绑定二维码

### 4.1 流程

1. 用户在网页完成主认证（密码等）后，请求绑定新的 TOTP 认证器。
2. 服务端生成 20 字节随机 `secret`，以 Base32 编码；生成 `bid`；从提交地址推导 `dom`（host[:port]）与 `path`（path+query），组装绑定载荷（§4.3）。绑定载荷**不签名**。
3. 网页展示绑定二维码，**一次性展示**，过期时间建议 ≤600s。
4. App 扫码 → 解析 JSON → 校验版本、必填字段、格式、`exp`（若有）。**不验签**（§5）。
5. App 展示“地址确认”页面：显示二维码中的 `iss`、`acc`、`dom`、`path`，并允许用户填写**本地备注** `label`（可选，≤64 字符，见 §13.3）。用户确认后，App 写入安全存储：`bid`、`sec`、`dom`、`path`、`iss`、`acc`、`alg`、`dig`、`per`、`label`，并钉住 `dom` 的注册域名、`path` 原值与完整提交地址 `https://{dom}{path}`。
6. App 立即用 `sec` 计算一次动态码，调用 `POST /totp/v1/bindings/{bid}/confirm` 完成绑定确认。
7. 服务端校验动态码（同样使用三时间窗）后，把绑定置为 `confirmed`；未确认的绑定不得用于登录。

**本地备注 `label`（强制约束）**

1. 只在“地址确认”步骤由用户填写，也可在账户详情中后续编辑或清空；跳过不影响绑定。
2. 仅存本地（安全存储或本地数据库），**不得**进入绑定二维码、不得随任何请求上行（包括绑定确认与登录提交）。
3. **不得**出现在日志、分析事件、崩溃报告、遥测数据中；与其他账户字段一样按敏感数据对待（S13）。
4. 长度 ≤64 字符；Unicode NFC；禁止换行与 C0 控制字符。超长或含非法字符时只拒绝该备注，不得连带拒绝绑定。
5. 备注不参与任何安全判定：候选反查（§6.2）不看备注，服务端也不得接收备注。

### 4.2 二维码编码

二维码内容为 **UTF-8 编码的紧凑 JSON 文本**（无 BOM、无换行、字段间无多余空白）。App 必须按 JSON 严格解析，不得做“宽松修复”。

### 4.3 字段定义

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| `t` | string | 是 | 固定值 `"totp-bind"` |
| `v` | integer | 是 | 固定值 `1` |
| `bid` | string | 是 | 绑定标识，`b_` + base64url(16 字节随机)，长度 24–64，仅 `[A-Za-z0-9_-]`；不得含任何用户身份信息 |
| `iss` | string | 是 | 签发方展示名，1–64 字符，NFC，禁止换行与控制字符 |
| `acc` | string | 是 | 账户标识（邮箱或用户名），1–255 字符，NFC，禁止换行与控制字符 |
| `sec` | string | 是 | TOTP 共享密钥，RFC 4648 Base32，**大写、无 `=` 填充**，解码后 16–64 字节（≥128 bit，推荐 20 字节 / 160 bit） |
| `alg` | string | 是 | `"SHA1"` \| `"SHA256"` \| `"SHA512"`，默认 `"SHA1"` |
| `dig` | integer | 是 | `6` 或 `8`，默认 `6` |
| `per` | integer | 是 | 时间步长（秒），`30` 或 `60`，默认 `30` |
| `dom` | string | 是 | 站点域名 `host[:port]`，IDNA A-label 小写，默认端口省略；不得含 scheme、路径、userinfo、查询串或 fragment。App 必须钉住其**注册域名**（用完整 PSL 推导，§7.3） |
| `path` | string | 是 | 提交路径，**含查询串、原样保留**（如 `/totp/v1/verify` 或 `/dtm/ulr?ma=xxx`）；必须以 `/` 开头，不得含 fragment、空白或控制字符。App 必须钉住该字符串（§7.3） |
| `iat` | integer | 是 | 签发时间，Unix 秒 |
| `exp` | integer | 否 | 失效时间，Unix 秒；若存在，App 必须拒绝 `now > exp` 的绑定二维码 |

> 绑定载荷**不包含** `sig`、`kid`、`pub` 或任何公钥字段：v1 不对绑定载荷签名，App 也不验签（§5）。

### 4.4 示例

```json
{"t":"totp-bind","v":1,"bid":"b_3nS0kq9uV2xJ0mQw1sT4aA","iss":"Example Corp","acc":"alice@example.com","sec":"JBSWY3DPEHPK3PXPJBSWY3DPEHPK3PXP","alg":"SHA1","dig":6,"per":30,"dom":"auth.example.com","path":"/totp/v1/verify","iat":1762396800,"exp":1762397400}
```

机器可读定义见 [`schemas/binding-qr.schema.json`](./schemas/binding-qr.schema.json)。

> 标准型 TOTP 账户不使用本二维码，而是通过 `otpauth://totp` URI 或手动录入建立，见 §13。

## 5. 绑定载荷完整性（无签名）

v1 **不对绑定载荷签名**，也不预置、下载或分发任何公钥：

1. 绑定二维码不包含 `sig`、`kid`、`pub` 或任何签名/公钥字段（§4.3）。
2. App **不验签**；扫码解析并校验字段格式与 `exp` 后即可展示确认页。
3. 服务端**不持有签名密钥**，不提供 `well-known` / JWKS / 公钥分发端点。
4. 因此绑定二维码是「扫到什么信什么」：它不能证明来源可信（§3.2 T2、§10）。防钓鱼只能依赖用户在确认页核对 `iss`、`acc`、`dom` 与 `path`，以及后续登录时的注册域名比对（§7.3）。
5. 未来版本若引入签名，必须提升 `v` 并在新版规范中完整定义，不得在 v1 中预留字段。

> 本章保留编号以维持与旧版规范、测试用例的交叉引用；v1 不含任何绑定完整性密码学机制。

## 6. 登录流程与登录二维码

### 6.1 流程

> 本节仅适用于**扫码型账户**（有钉住地址）。标准型账户没有钉住地址，不参与扫码提交，也不会成为候选账户（§13.1）。

1. 登录页请求服务端签发登录 `token`（`POST /totp/v1/login/token`），请求**必须**携带 `account`（页面已确定待认证账户）。
2. 服务端在**当前浏览器会话**上生成 16 或 24 位 token（参考实现取 24 位），记录 `{token, session_id, account, issued_at, expires_at}`，返回 `token`、`expires_at` 与登录二维码载荷。
3. 网页展示二维码（同时可展示倒计时）。
4. App 扫码 → 解析 → 校验 `t`、`v`、`exp`（仅用于本地提示）→ 按 §6.2 用二维码中的 `url` 比对本地钉住的 `dom`。
5. **候选为 0**：App 必须本地终止，不计算动态码、不发起任何网络请求，提示“未找到与该二维码匹配的站点”。
6. **候选唯一**：直接使用该账户的密钥计算当前时间步的动态码。
7. **候选多个**（同一注册域名下挂多个账户）：**仅**在候选集合内让用户选择；不得跨不同注册域名混合候选，也不得展示候选集合之外的账户；用户取消则终止。
8. 选定账户后，向其**钉住的完整提交地址**（`scheme + dom + path`）发起 `POST`，请求体 `{"code":"123456","token":"..."}`，使用 HTTPS，`Content-Type: application/json`，不接受重定向。**登录二维码中的 `url` 任何情况下都不得作为提交目标；路径只来自绑定时钉住的 `path`**。
9. 服务端完成 §8 校验后，将当前浏览器会话标记为已认证；网页轮询/长连接获知结果。
10. token 的一次性使用、失败次数与限流属于站点建议项（§8.4），不构成本流程的强制要求。

### 6.2 账户反查与候选选择算法

设登录二维码声明的站点域名为 `U`（来自二维码，**不可信**）：

| 步骤 | 规则 |
| --- | --- |
| A1 | 校验 `U` 符合 §7.2 的域名形式；失败 → 本地终止（候选为 0） |
| A2 | 遍历本地**所有扫码型账户**的钉住记录 `dom`，用**客户端完整 PSL** 推导 `U` 与 `dom` 的注册域名，相等即命中；命中的账户构成候选集合 `S` |
| A3 | 同一账户存在多条绑定记录时，只保留最近确认的一条，视为单一候选；标准型账户永远不进入 `S` |
| A4 | `\|S\| = 0` → 本地终止；不计算、不发请求 |
| A5 | `\|S\| = 1` → 自动选择该账户 |
| A6 | `\|S\| > 1` → 仅在 `S` 内让用户选择；列表必须展示 `issuer` / `account` / `dom` + `path`；不得展示 `S` 之外的账户；用户取消 → 终止 |
| A7 | 用选中账户的 `sec` 计算动态码，向**该账户自己钉住的完整提交地址**提交 `{code, token}` |
| A8 | `U` 只参与 A2 的比对，任何情况下都不得作为提交目标（S1）；**多点匹配时这条依然成立** |

补充约束：

1. 候选集合的判定只看“登录 `url` vs 钉住 `dom` 的注册域名”，**不看** `issuer`/`account` 文本。
2. **路径不参与候选判定，也不来自登录二维码**：提交路径只使用绑定阶段钉住的 `path`。
3. 服务端不得根据 `account` 反推或改写提交目标；它只负责按 token 绑定的账户选择密钥并校验。
4. 该算法必须完全在本地完成：候选为 0 时网络层不得出现任何出站请求（DNS 查询也属于出站请求）。

### 6.3 二维码编码

与绑定二维码一致：UTF-8 紧凑 JSON 文本。

### 6.4 字段定义

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| `t` | string | 是 | 固定值 `"totp-login"` |
| `v` | integer | 是 | 固定值 `1` |
| `url` | string | 是 | 站点域名，如 `qq.example.com`；**不带 scheme、不带路径、不带查询串、不含 userinfo**；仅用于与钉住的 `dom` 比对 |
| `token` | string | 是 | 会话标识，16 或 24 个 base64url 字符（`[A-Za-z0-9_-]`） |
| `exp` | integer | 是 | 失效时间，Unix 秒；`exp - now` 必须 ≤ 60 |

登录二维码 **不得** 包含：TOTP `sec`、用户密码、会话 Cookie、用户真实身份信息、任何长期凭据；也不得包含 `bid`、绑定地址、`device_id` 或本节未声明的任何字段。

### 6.5 示例

```json
{"t":"totp-login","v":1,"url":"qq.example.com","token":"9tQm3vK8pR2xYb7cLw5nZ0aF","exp":1762396860}
```

## 7. 站点域名规范化与比对

### 7.1 为什么要规范化

`QQ.Example.COM` 与 `qq.example.com` 在语义上是同一个站点。若按字符串逐字比较，会导致合法二维码被拒；若按“包含/后缀匹配”比较，又会放过 `qq.example.com.evil.test` 这类攻击域名。因此必须“先规范化、再按注册域名比对”。

### 7.2 站点域名规范化（D1–D5）

输入为登录二维码的 `url`，或绑定载荷 `dom` 的 host 部分：

| 步骤 | 规则 |
| --- | --- |
| D1 | 必须是字符串；长度 1–255；不得有前后空白；不得含控制字符 |
| D2 | 不得包含 scheme（`://`）、路径（`/`）、查询串（`?`）、fragment（`#`）或 userinfo（`@`） |
| D3 | Unicode 域名按 IDNA ToASCII 转 punycode；转小写；去掉结尾的 `.` |
| D4 | 结果不得为空；IPv6 使用压缩小写形式并保留方括号 |
| D5 | 输出仅域名；`dom` 可带非默认端口 `:port`（端口不参与后续比对），登录 `url` 不得带端口 |

绑定载荷的 `path` 另行校验：必须以 `/` 开头，可含查询串且**原样保留**（不排序、不重编码），不得含 fragment、空白或控制字符（§4.3）。`path` 不参与登录比对。

### 7.3 比对规则（M1–M3）

设登录二维码声明的站点域名为 `U`，绑定阶段钉住的站点域名为 `dom`：

| 规则 | 内容 |
| --- | --- |
| M1 | `U` 必须符合 §7.2 的域名形式；否则不匹配 |
| M2 | 用**客户端完整 PSL**（ICANN + PRIVATE 段）分别推导 `U` 与 `dom` 的注册域名，二者必须完全相等。服务端**不承担**该推导与比对 |
| M3 | 任一不满足 → 不匹配；App 立即终止，不计算动态码、不发起请求 |

> 说明：
> - 登录二维码不携带路径，**路径不参与比对**；提交目标固定为绑定阶段钉住的 `scheme + dom + path`。
> - 端口不参与比对；安全性依赖注册域名相等。
> - 相似域名（如 `qq.example.com.evil.test`）只会因 M2 失败而被拒绝；任何“相似域名告警”都只是 UI 提示，不作为安全机制或验收项。

### 7.4 判定示例

| 钉住 `dom` | 登录 `url` | 结果 | 理由 |
| --- | --- | --- | --- |
| `qq.example.com` | `qq.example.com` | 命中 | 完全相同 |
| `qq.example.com` | `QQ.Example.COM` | 命中 | D3 小写 + IDNA |
| `qq.example.com` | `login.example.com` | 命中 | 注册域名同为 `example.com` |
| `qq.example.com` | `qq.example.com.evil.test` | 拒绝 | 注册域名为 `evil.test` |
| `qq.example.com` | `evil.test` | 拒绝 | 注册域名不同 |
| `qq.example.com` | `qq.example.com/login` | 拒绝 | D2 含路径 |
| `qq.example.com` | `https://qq.example.com` | 拒绝 | D2 含 scheme |
| `qq.example.com` | `user@qq.example.com` | 拒绝 | D2 含 userinfo |

## 8. 登录 token 与统一错误

> 本章描述参考实现的做法，除“提交时原样回传 `token`”外，均属 **B 类实现建议**（§0、§11）。token 的一次性、失败计数与限流不构成协议要求，也不作为验收项。

### 8.1 状态机（建议）

```
                签发
                 │
                 ▼
             ┌────────┐   成功校验且未过期     ┌──────────┐
             │ issued │ ───────────────────► │ consumed │
             └────────┘                        └──────────┘
               │    │
     5 次失败  │    │ 到达 expires_at
               ▼    ▼
        ┌──────────┐ ┌─────────┐
        │ exhausted│ │ expired │
        └──────────┘ └─────────┘
               │
               └── 会话结束 / 绑定解绑 → revoked
```

状态一旦离开 `issued` 即不可恢复；任何失败都不得“续期”或“重置计数”。

### 8.2 签发约束（建议）

| 项目 | 建议 |
| --- | --- |
| 形式 | 16 或 24 个 base64url 字符（`[A-Za-z0-9_-]`）；参考实现取 24 |
| 随机源 | CSPRNG（参考实现 18 字节 → 24 字符） |
| 有效期 | 建议 ≤60 秒；服务端以自身时钟判定，不依赖客户端时间 |
| 绑定对象 | `session_id`（建议）+ `account`（签发时必填）+ 签发时间 + 尝试计数 |
| 账户维度 | token 只对签发时指定的 `account` 生效；提交体不再携带 `account` |
| 存储 | 建议只存 SHA-256 摘要或等效不可逆形式；日志不得记录明文 token |
| 传输 | 仅出现在登录页响应体与二维码中；不得写入 URL query、Referer、第三方资源 |
| 并发 | 同一会话可以存在多个未消费 token（多标签页），每个 token 独立计数 |

### 8.3 校验约束（建议）

服务端按下述顺序校验，任一失败即失败：

1. 请求体含 `token` / `code`，均为字符串；
2. `token` 形状合法（16 或 24 个 base64url 字符）；
3. `token` 存在（按摘要查找）、状态未消费、未作废；
4. `now <= expires_at`（无宽限，不允许客户端时钟影响）；
5. `token` 的 `session_id` 与请求会话一致（若实现采用会话绑定）；
6. 按 token 绑定的 `account` 查找**已确认且未解绑**的绑定；不存在则失败；
7. `code` 的位数与绑定记录的 `dig` 一致（6 或 8 位十进制数字）；
8. TOTP 在 `t-1 / t / t+1` 三个时间窗之一命中（算法、周期取自绑定记录，不取自请求）；
9. （建议）该 `(binding, timestep)` 此前未被成功使用。

> 协议只约定第 1、6、7、8 步所依赖的字段与语义（A 类）；其余步骤由接入方按自身安全水位实现（B 类），失败时是否统一响应也由接入方决定（§8.5）。
>
> `account` 只用于**选择密钥**，不参与任何地址解析：服务端不得根据 `account` 反推、改写或重定向提交目标（S1）。

### 8.4 一次性、失败计数与限流（建议，非验收）

RFC 6238 本身不要求一次性消费、失败锁定或限流；这些属于站点自身的安全水位。参考实现采用下列参数，接入方可自行调整或不实现：

| 维度 | 阈值（参考实现） | 超限行为 |
| --- | --- | --- |
| 单 token 失败次数 | 5 次 | 置 `exhausted`，此后即使提交正确码也拒绝；必须重新签发 |
| 单会话签发速率 | 5 次 / 60 秒 | 返回 `429 rate_limited` |
| 单 IP 签发速率 | 30 次 / 60 秒 | 返回 `429 rate_limited` |
| 单 IP 校验速率 | 30 次 / 60 秒 | 返回 `429 rate_limited` |
| 绑定确认失败 | 5 次 | 绑定置 `invalid`，必须重新发起绑定 |

限流拒绝的响应体建议与业务失败响应体格式一致（仅 `error` 值不同），且**不应**透露出 token 是否存在、是否过期等信息。

> 上述各项均**不是**验收条件；§9 中标为“参考”的用例只用于验证参考实现。

### 8.5 统一错误响应（建议）

参考实现对以下失败——token 未知、已过期、已消费、已作废、跨会话、绑定不存在、绑定未确认、验证码错误、重放、次数耗尽——返回同一响应：

- HTTP 状态码：`401`
- 响应体（字段顺序不保证，值必须完全一致）：

```json
{
  "error": "authentication_failed",
  "message": "认证失败，请重新发起登录",
  "request_id": "req_01J9Z3K7WQ8N2T5B6M4C0X1Y7V"
}
```

约束：

1. `message` 为固定文案，不得包含原因、字段名、剩余次数、剩余时间；
2. `request_id` 每次请求唯一，仅用于日志关联，不得编码失败原因；
3. 响应时间应当与失败原因无关：对未知 token 也必须执行一次等价的 HMAC 计算与常量时间比较（使用固定的假密钥），避免计时旁路；
4. `400` 仅用于请求体格式错误（非 JSON、缺字段、类型错误），文案同样为通用文案 `"请求格式无效"`；不得用它暗示 token 状态；
5. `429` 仅用于限流，且对“token 有效/无效”不做区分。

错误响应机器可读定义见 [`schemas/error.schema.json`](./schemas/error.schema.json)。

## 10. 已知局限

本节明确声明：**本协议不是抗钓鱼的强认证方案**，不能替代 WebAuthn/FIDO2。部署方必须向用户与审计方如实说明以下局限。

1. **无法防御“真地址中继”钓鱼**：攻击者可以搭建钓鱼页，却在页面二维码中填入**真实的** `url`（站点域名是公开信息）。此时 App 的域名比对会命中，动态码会被提交到真实服务端，但登录 `token` 属于攻击者的浏览器会话，攻击者因此可能完成对该会话的认证。域名比对只能阻断“假地址”类钓鱼，不能阻断“借用真地址 + 中继 token”的攻击。
2. **共享密钥仍在二维码里**：绑定二维码包含 TOTP `sec` 的明文（Base32）。任何能截屏、录屏、读取剪贴板或截获展示界面的攻击者都可复制该密钥，之后完全离线生成动态码。绑定过程必须一次性、短时、在可信设备上完成。
3. **本质仍是共享秘密**：TOTP 是共享密钥方案，服务端被攻破即可伪造任意动态码；本协议不改变这一点。
4. **无设备证明**：协议不校验 App 是否为官方版本、设备是否被 root/越狱、密钥是否在硬件安全模块内。安全存储的强度完全依赖操作系统能力与 App 实现质量。
5. **动态码熵有限**：6 位码只有 10^6 空间，三时间窗把有效空间扩大到 3×10^6；建议接入方自行实施“失败作废 + 限流”（B 类，RFC 6238 不要求）。若未实施，动态码可被在线枚举。
6. **依赖时钟**：设备与服务端时钟偏差超过一个时间步（`period`，默认 30 秒）会导致验证失败；NTP 被劫持可能造成可用性问题。详见 §13.7。
7. **TLS 是必要条件而非增强项**：若攻击者能对 `dom` 的源实施可信证书中间人攻击，本协议全部防护失效。必须启用 HSTS、证书校验与安全的重定向策略。
8. **会话绑定依赖 Cookie 模型**：登录 `token` 建议与会话 Cookie 绑定（B 类）；若部署方的会话实现存在 CSRF、会话固定或 Cookie 作用域缺陷，攻击者可绕过会话绑定。服务端应同时实施 CSRF 防护与 `HttpOnly; Secure; SameSite` Cookie 策略。
9. **二维码展示通道本身不可信**：被恶意扩展、屏幕共享、远程桌面篡改的登录页可以展示任意二维码。协议只能保证“App 不会把码发到陌生地址”，不能保证“用户看到的页面是可信页面”。
10. **不提供不可否认性与审计完整性**：成功提交只代表“某设备在某个时间窗内掌握了共享密钥”，不能证明具体自然人身份。
11. **不支持离线登录，且增强型账户默认不提供可读动态码**：提交必须到达服务端；离线场景下增强型账户默认无法完成认证。用户可在本地认证并确认风险后开启 S18 显示开关，或按 §15 导出单账户 `otpauth://` 二维码；两者都会削弱防钓鱼能力，开启/导出前必须明确提示。
12. **不是长期会话令牌方案**：本协议不签发、不刷新任何 bearer token；把它当作“扫码登录”使用会引入完全不同的威胁模型，超出本规范范围。
13. **绑定二维码的 `exp` 仅由 App 本地判断**：`exp` 不参与任何密码学校验（v1 无签名，§4.3、§5），截获未确认的旧绑定二维码者无法改变提交地址（地址已被 App 钉住），但可能延长“本地认为未过期”的窗口。服务端应保证 `bid` 一次性（确认后不得重复确认）并缩短绑定二维码有效期，以降低该风险。
14. **参考服务端的状态仅存于进程内存**：登录 `token`、会话、绑定、重放记录与限流计数都保存在单进程内存中，进程重启即全部丢失，多实例之间也不共享。因此参考实现**仅适用于单实例部署与本地验证**；生产环境应换成共享存储（如 Redis / 数据库），并对 token 的一次性消费、失败计数、时间步重放记录与限流保持原子性。

## 13. 与标准 TOTP（RFC 6238）的兼容性

本章规定：App **同时是一个完整可用的标准 TOTP 认证器**，扫码提交只是叠加在标准 TOTP 之上的增强能力。两类账户在同一 App 内共存，但数据模型、界面与安全要求严格区分，不得混用。

### 13.1 双模式定位

| 模式 | 建立方式 | 动态码使用方式 | 是否钉住提交地址 |
| --- | --- | --- | --- |
| **标准型账户（standard）** | `otpauth://totp` URI 导入，或手动录入 | 用户在任意网站手动输入 / 复制 | 否 |
| **扫码型账户（scan-enhanced）** | 本协议 §4 的绑定二维码 | App 扫码后自动提交到钉住地址 | 是 |

强制规则：

1. 标准型账户**不得**参与扫码提交流程，也不存在 `bid`、`dom`、`path` 等绑定字段；它**永远不进入** §6.2 的候选集合，即使其 `issuer/account` 与某个扫码站点同名。
2. 扫码型账户**不得**由 `otpauth://` URI 或手动录入创建；只能走绑定流程，以确保 `dom` 与 `path` 同时落地。
3. 不存在“自动升级/自动降级”，也不存在就地转换账户模式的入口：
   - 标准型 → 扫码型：必须由服务端重新发起绑定（新 `sec`、新 `bid`），旧条目不保留任何信任。
   - 扫码型 → 标准型：**不得**清空 `dom` / `path` / `bid` 后把原账户就地改成标准型。用户可按 §15.2 导出单账户 `otpauth://` 二维码，在另一认证器中建立一条**独立副本**；该副本没有钉住地址，原增强型账户不受影响，且仍默认不展示即时码（S15、S18）。
4. 同一 `issuer/account` 同时存在两种模式时，UI 必须明确标注模式，禁止凭据混用。

### 13.2 `otpauth://totp` URI 支持

采用事实标准（Google Authenticator Key URI Format）：

```
otpauth://totp/{label}?secret={base32}&issuer={issuer}&algorithm={alg}&digits={digits}&period={period}
```

解析规则（全部为强制）：

| 步骤 | 规则 |
| --- | --- |
| U1 | scheme 必须为 `otpauth`，host 必须为 `totp`（大小写不敏感）；`hotp` 及其他类型一律拒绝 |
| U2 | `label` 为 percent-encoded UTF-8；可写成 `issuer:account`。若同时提供 query 参数 `issuer`，两者必须完全一致，否则拒绝导入 |
| U3 | `secret` 必填；Base32（RFC 4648），大小写不敏感，允许空格与 `=` 填充；解码后必须 ≥10 字节（兼容历史密钥），**低于 16 字节（128 bit）时 App 应提示密钥强度不足**；存储时重新编码为大写、无填充 |
| U4 | `algorithm` 可选，`SHA1` / `SHA256` / `SHA512`（大小写不敏感），默认 `SHA1`；其他值拒绝 |
| U5 | `digits` 可选，`6` 或 `8`，默认 `6`；其他值拒绝 |
| U6 | `period` 可选，正整数秒，默认 `30`；标准型账户支持**任意正整数**（如 15、45、90；实现可设置合理上限，例如 1–3600） |
| U7 | 未知参数忽略；同名参数出现多次一律拒绝；`counter`（HOTP 专用）出现即拒绝 |
| U8 | URI 含共享密钥：不得写入日志、剪贴板（用户主动粘贴除外）、分析事件、备份明文；导入后不得在 UI 中常驻明文展示 |
| U9 | 手动录入等价于构造同样的 URI：`secret` 必填，`issuer`/`account` 可选，其余字段按 U4–U6 默认与校验 |

示例：

```
otpauth://totp/Example%20Corp:alice%40example.com?secret=JBSWY3DPEHPK3PXP&issuer=Example%20Corp&algorithm=SHA256&digits=8&period=60
```

### 13.3 数据模型差异

| 字段 | 标准型 | 扫码型 | 说明 |
| --- | --- | --- | --- |
| `type` | `standard` | `scan` | 决定后续所有流程分支 |
| `issuer` / `account` | 有 | 有 | 用于展示与查找 |
| `label`（本地备注） | 有（可选） | 有（可选） | 用户自定义备注，≤64 字符；**仅存本地**，不进二维码、不上送、不写日志，可后续编辑（§4.1） |
| `secret` | 有 | 有 | 均必须存入安全存储 |
| `algorithm` / `digits` / `period` | 有（period 任意正整数） | 有（v1 仅 30 / 60） | 见 §13.6 |
| `bid` | 无 | 有 | 绑定标识 |
| `submitUrl` | **无** | 有，写入后不可变 | 只能通过重新绑定变更 |
| `dom` / `path` | 无 | 有 | 扫码型的比对依据与提交目标；写入后不可变 |
| 动态码展示 | 展示明文 + 倒计时 | 默认不展示；开启 S18 开关后展示明文 + 倒计时 | 见 §13.4、S15、S18 |
| 动态码复制 / 导出 / 分享 | 可以（复制；用户主动操作） | 默认不提供；开启 S18 后允许复制；导出 / 分享即时码仍不提供 | 见 §15.3 |

### 13.4 界面差异

1. 标准型账户：展示动态码、环形倒计时与“复制动态码”；**不得**提供“复制密钥”入口（密钥只在导入时可见一次）。标准型账户没有钉住地址，**不参与扫码提交**，也不出现在候选列表（§6.2）。
2. 扫码型（增强型）账户：
   - **默认不展示 6/8 位动态码**，默认不提供复制、导出、分享入口，也不得把动态码写入剪贴板；
   - 只有用户按 S18 完成本地认证并勾选风险确认、显式开启“显示动态码”开关后，界面才可展示即时码与倒计时，并允许复制；
   - 开关关闭时必须**立即隐藏并清空**界面值与内存缓存；
   - 无论开关是否开启，动态码都只用于展示或同一次扫码提交，提交路径、候选匹配与提交目标不变；
   - SDK 默认不得无条件向调用方暴露即时码（不得提供常驻的 `getCode()` 公共 API）；开关开启时，只允许受信任的已认证 UI 获取当前显示值；
   - 即时码的导出 / 分享入口仍然禁止（长期密钥的二维码导出按 §15，不属于即时码导出）；
   - 动机：默认不可见可降低截屏、录屏、剪贴板、无障碍服务、恶意插件与注入调用导致的泄露面；开启开关是用户显式接受风险后的例外，而不是默认行为。
3. 扫码型账户的详情页展示钉住的 `submitUrl`（只读）与本地备注 `label`（可编辑）；标准型账户展示来源（URI / 手动录入）与本地备注 `label`（可编辑）。备注编辑不触发任何网络请求。
4. 两类账户在列表中必须有可见的模式标签；扫码型账户不得出现在“手动输入动态码”的提交流程中（S18 只影响展示，不新增提交入口）。

| 要求 | 标准型 | 扫码型 |
| --- | --- | --- |
| S1 提交目标唯一来源（A） | 不适用（无提交） | 必须 |
| S2 站点域名比对（A） | 不适用 | 必须 |
| S3 载荷字段与格式（A） | 不适用（用 otpauth URI） | 必须 |
| S4 TOTP 参数语义（A） | 计算遵循 RFC 6238 | 必须 |
| S5 提交格式（A） | 不适用（无提交） | 必须 |
| S6–S8、S10、S11（B） | 不适用（无 token） | 参考建议 |
| S9 时间步重放（B） | 由非扫码流程自行决定 | 参考建议 |
| S12 解绑与轮换（B） | 不适用 | 参考建议 |
| S13 密钥与日志保护（B） | 建议 | 建议 |
| S14 管理令牌（B） | 不适用 | 参考实现强制 |
| S15 即时码隔离 | 不适用（允许展示与复制） | 默认不展示 / 不复制；开启 S18 后可展示与复制 |
| S16 备份与迁移作用域 | 不允许（仅扩展提供） | 不允许（仅扩展提供） |
| S17 单账户二维码导出 | 允许（打开前本地认证） | 允许（本地认证 + 二次确认） |
| S18 即时码显示开关 | 不适用 | 必须 |

补充约束：

- 标准型账户天然**不具备防钓鱼能力**：动态码可被钓鱼页面诱导输入。App 应在首次导入与账户详情中明确提示，不得暗示其具有 §7 的地址比对保护。
- 标准型账户不属于任何扫码候选集合，**不得**因 `issuer/account` 与某站点相似而被自动关联；扫码提交只认钉住地址。
- 增强型账户可按 §15 导出单账户 `otpauth://` 二维码（屏幕展示、长期密钥），但必须二次确认并提示“防钓鱼优势失效”；除此之外不得把 `sec` 写入文件、剪贴板、日志或分享内容。
- 标准型账户可按 §15 导出二维码，但 App **不得**提供“复制密钥”文本入口；二维码同样是屏幕一次性展示，关闭即清空。

### 13.6 非 SHA1 参数的处理

1. **参数来源**：`alg`、`dig`、`per` 只来自绑定载荷或 `otpauth` URI，并在绑定确认时写入绑定记录；不接受提交请求中的覆盖。
2. **App 计算**：必须严格使用二维码中的 `alg` / `dig` / `per`，不得“缺省当作 SHA1”或忽略字段；字段缺失即为非法载荷。
3. **服务端校验**：算法、位数、周期由 token 绑定的 `account` 对应的**绑定记录**决定，请求体只允许 `token` + `code`，客户端无法在提交时指定或降级算法。绑定不存在 / 未确认 / 已解绑一律失败。
4. **密钥长度建议**（RFC 6238 §5.1 / RFC 4226 R6）：共享密钥至少 128 bit；推荐与哈希输出等长——SHA1 ≥20 字节、SHA256 ≥32 字节、SHA512 ≥64 字节。v1 绑定载荷允许 16–64 字节；参考实现默认生成 20 字节 SHA1 密钥，使用 SHA256/SHA512 的部署方应生成 32/64 字节密钥。
5. **位数校验**：`dig=8` 时只接受 8 位数字，`dig=6` 时只接受 6 位；长度不符直接失败，不做截断或补零。
6. **周期**：扫码型 v1 的 `per` 仅允许 30 / 60（见 §4.3、JSON Schema）；标准型支持任意正整数（U6）。两者都由绑定载荷或 URI 明确携带，不存在隐式默认。
7. **unknown algorithm**：任何未知 `alg` 值必须在保存绑定 / 导入 URI 前即被拒绝，不得回退到 SHA1。

### 13.7 校验窗口与时间偏差策略

1. **窗口定义**：服务端只接受 `{t-1, t, t+1}` 三个时间步（`t = floor(server_now / period)`），即最多 ±1 个周期。`period=30` 对应 ±30 秒，`period=60` 对应 ±60 秒；标准型账户在 App 内展示时同样按各自 `period` 计算。
2. **时钟权威**：服务端时钟是唯一权威。客户端时间、二维码中的 `exp` 仅用于本地提示与 token 失效，不参与 TOTP 判定。
3. **偏差处理**：设备应启用 NTP；若与服务端持续偏差超过 `period / 2`，App 应提示校准时间。服务端**不得**因为客户端偏差而扩大窗口（例如不得放宽到 ±2 步）。
4. **边界抖动**：±1 窗口仅用于吸收网络延迟与临界抖动，不是“容错放宽”；参考实现会记录同一 `(binding, timestep)`，窗口内重放一律拒绝（S9，B 类实现建议）。
5. **绑定确认**：使用与登录完全相同的窗口与参数；确认成功后**同样写入** `(bindingId, timeStep)` 重放记录，因此确认所用的时间步不能立即用于首次登录。App 应在确认后使用下一个时间步的动态码登录（等待一个 `period` 或重新计算），避免“确认码即登录码”的窗口内重放。
6. **标准型账户**：由其他系统校验时，建议同样采用 ±1 窗口；本协议不强制，但 App 的本地计算必须与 RFC 6238 完全一致（TC-23 的向量可直接复用 `server/test/totp.test.ts`）。

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| TC-21 | 创建 `SHA256 / 8 位 / 60 秒` 绑定并完成登录 | 确认与登录均成功 |
| TC-23 | `otpauth://` 解析边界（`hotp`、重复参数、issuer 冲突、非法 secret） | 全部拒绝；合法 URI 归一化为标准字段 |

## 14. 浏览器扩展的备份与迁移（移动客户端不适用）

本章定义**浏览器扩展**侧账户备份、换机迁移与第三方导入的统一格式。备份完全在扩展本地生成与解析，本协议的服务端接口不参与备份的创建、加密或校验。

> **作用域限定**：本章仅适用于浏览器扩展。移动端三端（Android / iOS / 鸿蒙）**不提供**账户导出、导入或迁移功能；移动端的 TOTP 密钥只能留在设备安全存储（Keystore / Keychain / 等效机制）内，不得以文件、剪贴板或任何外部可读形式离开设备。

### 14.1 目标与边界

1. 本章所有“导出 / 导入 / 备份文件 / `authenticator.txt` / 迁移二维码”规则**仅适用于浏览器扩展**；移动端不得实现本章任何导出入口。
2. 浏览器扩展的备份必须能完整恢复两类账户：标准型账户（`otpauth://` / 手动录入）与增强型账户（含钉住地址、`bid` 与本地备注 `label`）。
3. 备份包含 TOTP 共享密钥 `sec`，属于**长期凭据**，敏感级别等同于密码；必须按 §14.3 支持口令加密，并在导出时给出风险提示。
4. 备份**不得**包含：动态码、登录 `token`、会话 Cookie、请求日志、任何服务端响应。
5. 导入过程必须完全离线：不得因导入而发起地址解析、DNS 查询或提交请求。
6. **与 S15 / S17 的关系**：S15 管的是**即时码**默认隔离（可由 S18 开关显式放开），S17 管的是单账户长期密钥二维码导出（§15，屏幕展示、全端可用），本章管的是**备份文件**（仅浏览器扩展）。三者不是同一能力；备份导出是用户显式发起的长期凭据迁移操作，必须二次确认。导入后的增强型账户仍默认不展示即时码，除非用户另行开启 S18。
7. **移动端不适用**：移动端不提供本章的导入导出能力，也不得把密钥写入备份文件、云盘、剪贴板或分享面板。§15 的单账户 `otpauth://` 二维码屏幕导出不属于本章的备份/迁移文件，按 §15 执行（增强型仍需二次确认）。

### 14.2 统一 JSON 备份 schema（v1）

顶层对象（明文形态）：

```json
{
  "format": "totpscan-backup",
  "version": 1,
  "encrypted": false,
  "exportedAt": 1762396800,
  "accounts": [
    {
      "type": "standard",
      "issuer": "Example Corp",
      "account": "alice@example.com",
      "label": "工作",
      "secret": "JBSWY3DPEHPK3PXP",
      "algorithm": "SHA1",
      "digits": 6,
      "period": 30
    },
    {
      "type": "scan",
      "issuer": "Example Corp",
      "account": "alice@example.com",
      "label": "公司登录",
      "secret": "JBSWY3DPEHPK3PXP",
      "algorithm": "SHA1",
      "digits": 6,
      "period": 30,
      "submitUrl": "https://auth.example.com/totp/v1/verify",
      "bid": "b_3nS0kq9uV2xJ0mQw1sT4aA"
    }
  ]
}
```

字段规则：

| 字段 | 类型 | 必填 | 约束 |
| --- | --- | --- | --- |
| `format` | string | 是 | 固定值 `"totpscan-backup"` |
| `version` | integer | 是 | 固定值 `1`；其他版本一律拒绝导入 |
| `encrypted` | boolean | 是 | 明文备份为 `false` |
| `exportedAt` | integer | 是 | 导出时间，Unix 秒 |
| `accounts` | array | 是（明文） | 账户数组，顺序即 UI 顺序 |
| `accounts[].type` | string | 是 | `"standard"` \| `"scan"`；未知值拒绝该条目 |
| `accounts[].issuer` | string | 是 | 1–64 字符，NFC |
| `accounts[].account` | string | 是 | 1–255 字符，NFC |
| `accounts[].label` | string | 否 | 本地备注，0–64 字符，NFC；空字符串视为无备注 |
| `accounts[].secret` | string | 是 | RFC 4648 Base32，大写、无 `=`、无空格；解码后 10–128 字节 |
| `accounts[].algorithm` | string | 是 | `SHA1` \| `SHA256` \| `SHA512` |
| `accounts[].digits` | integer | 是 | `6` 或 `8` |
| `accounts[].period` | integer | 是 | 标准型 1–3600；扫码型仅 30 / 60 |
| `accounts[].submitUrl` | string | 增强型必填 | §7.2 规范形式；标准型**不得**出现 |
| `accounts[].bid` | string | 增强型必填 | 绑定标识，格式同 §4.3 |

补充规则：

1. 标准型条目**不得**携带 `submitUrl` / `bid`；增强型条目缺失任一必填字段即视为损坏备份，整份备份拒绝导入（不得部分导入）。
2. `label` 只存本地；备份文件是它的唯一跨设备载体，导入后仍不得上传服务器或写入日志。
3. v1 导入器**必须忽略**未知字段（前向兼容），但**不得**忽略未知 `type` 或未知 `version`。
4. 不得在备份中写入动态码、时间步、使用记录或任何会话数据。

机器可读定义见 [`schemas/backup.schema.json`](./schemas/backup.schema.json)。

### 14.3 可选口令加密

加密形态的顶层对象：

```json
{
  "format": "totpscan-backup",
  "version": 1,
  "encrypted": true,
  "kdf": {
    "name": "scrypt",
    "salt": "<base64url ≥16 字节>",
    "N": 32768,
    "r": 8,
    "p": 1
  },
  "cipher": {
    "name": "AES-256-GCM",
    "iv": "<base64url 12 字节>",
    "tag": "<base64url 16 字节>"
  },
  "ciphertext": "<base64url>"
}
```

KDF 允许两种：

| `kdf.name` | 必填参数 | 最低强度 |
| --- | --- | --- |
| `"scrypt"` | `salt`、`N`、`r`、`p` | `N ≥ 2^15`、`r ≥ 8`、`p ≥ 1` |
| `"PBKDF2"` | `salt`、`hash`、`iterations` | `hash = "SHA-256"`、`iterations ≥ 600000` |

加密规则（强制）：

1. 盐 `salt` 必须为 CSPRNG 生成的 ≥16 字节，每次导出重新生成；禁止复用盐。
2. `iv` 必须为 CSPRNG 生成的 12 字节，且同一口令/同一盐下**绝不重复**。
3. 明文为 §14.2 明文对象的紧凑 JSON（UTF-8、无 BOM、无多余空白），其中 `encrypted` 固定为 `false`。
4. AAD 固定为 UTF-8 字符串，按以下顺序以单个 LF 拼接、末尾无换行：

```
TOTPSCAN-BACKUP-V1
version=1
kdf=<kdf.name>
salt=<kdf.salt>
iv=<cipher.iv>
```

5. 认证标签校验失败、口令错误、KDF 参数低于最低强度、字段缺失：一律**整体拒绝**，返回统一文案“备份无法解密或已损坏”，不得泄露是口令错误还是数据损坏，不得部分导入。
6. 加密信封中**不得**出现任何明文 `issuer` / `account` / `label` / `secret`；只允许出现 KDF 与 cipher 元数据。
7. 口令不得持久化、不得写入日志/剪贴板/崩溃报告；UI 不得回显口令。
8. 导出时若用户选择“不加密”，必须显示显著风险提示并二次确认；默认建议加密。

### 14.4 `authenticator.txt` 兼容导入（宽松解析）

用于浏览器扩展导入其他认证器导出的文本文件。解析必须宽松，但**不得**因宽松而降低校验强度。移动端不适用本节。

| 步骤 | 规则 |
| --- | --- |
| P1 | 按 UTF-8 解码；去除 BOM；`CRLF` / `CR` 统一为 `LF`；逐行 `trim` |
| P2 | 跳过空行，以及以 `#` 或 `//` 开头的注释行 |
| P3 | 行首为 `otpauth://totp`（大小写不敏感）时，按 §13.2 的 U1–U9 严格解析；`hotp` 行跳过并计数 |
| P4 | 行首为 `otpauth-migration://offline?data=` 时，按 §14.4.2 解码迁移载荷 |
| P5 | 其余行按“通用分隔行”解析（§14.4.1） |
| P6 | Base32 归一化：删除空格、制表符、连字符；转大写；去 `=` 填充；再按 §13.2 U3 校验长度与字符集 |
| P7 | 单行解析失败只跳过该行并计入 `skipped`，不得中止整份导入；不得把失败行的内容写入日志 |
| P8 | 只创建标准型账户。文本中即使出现 `submitUrl` / `bid` 也一律忽略；增强型账户只能通过绑定流程创建 |
| P9 | 导入完成后展示摘要：`imported` / `skipped` / `conflicts`；整个过程零出站 |

#### 14.4.1 通用分隔行

1. 分隔符优先级：制表符 → `|` → `;` → `,` → 连续 2 个及以上空格。命中第一个能产生 ≥2 个非空字段的分隔符后即按该分隔符切分。
2. 若任一字段形如 `key=value`（`issuer` / `account` / `secret` / `label`，大小写不敏感），按键值记录解析，字段顺序无关；`secret` 必填。
3. 否则按位置解析：
   - 3 个字段：`issuer`、`account`、`secret`；
   - 2 个字段：`account`、`secret`。
4. 无上述分隔符但含冒号时：恰好 2 段且第 2 段是合法 Base32 → `account:secret`；恰好 3 段且第 3 段是合法 Base32 → `issuer:account:secret`；其他情况跳过该行。
5. `issuer` / `account` 缺失时分别补空字符串与 `"未命名账户"`；`algorithm` 默认 `SHA1`、`digits` 默认 6、`period` 默认 30。
6. 同一文件中出现重复条目（`issuer` + `account` 完全相同）时保留第一条，其余计入 `skipped`。

#### 14.4.2 `otpauth-migration://offline?data=` 迁移二维码

1. `data` 参数先去除空白，再按 base64url 解码；若含 `+` / `/` / `=`，按标准 base64 解码。两种编码都接受。
2. 解码结果为 protobuf `MigrationPayload`：`otp_parameters`（字段 1，可重复）包含 `secret`（1，bytes）、`name`（2，string）、`issuer`（3，string）、`algorithm`（4，enum）、`digits`（5，enum）、`type`（6，enum）、`counter`（7，varint）。
3. 枚举映射：`algorithm` 0/未设置 → `SHA1`，1 → `SHA1`，2 → `SHA256`，3 → `SHA512`；`digits` 0/未设置 → 6，1 → 6，2 → 8；`type` 0/未设置或 2 → TOTP，1 → HOTP。
4. 只导入 TOTP；HOTP 条目跳过并计入 `skipped`。迁移载荷不含 `period`，统一按 30 秒导入。
5. `secret` 必须非空且通过 Base32 校验；`name` 作为 `account`，`issuer` 原样保留。
6. protobuf 未知字段必须忽略；解析失败或 `data` 为空时整条迁移行跳过，不影响其他行。
7. 迁移格式不携带钉住地址，因此**只能**生成标准型账户，不得生成或升级为增强型账户。

### 14.5 导出增强型密钥的二次确认（仅浏览器扩展）

1. 导出包含增强型账户的备份（无论是否加密）前，必须进行**二次确认**：先展示风险说明，再由用户显式确认（推荐再次输入设备口令 / 生物识别）。
2. 风险提示必须至少包含：
   - 备份包含可离线生成动态码的共享密钥；
   - 获得备份文件的人可在不知道账户密码的情况下冒充该账户；
   - 未加密备份等同于明文密码，必须存放在可信位置并及时删除；
   - 增强型账户的钉住地址也会被导出，恢复到其他设备后仍只向该地址提交。
3. 用户取消 → 不生成文件、不写临时文件、不留下可恢复的明文缓存。
4. 导出过程不得在 UI 展示 `sec`、不得写入剪贴板（用户主动选择“复制”除外）、不得写入日志。
5. 导出**不违反 S15**：S15 约束的是即时码默认不可见（S18 是显式开关），备份导出的是长期密钥，二者不冲突。导入后的增强型账户仍默认不展示即时码；若用户需要显示，必须重新通过 S18 的本地认证与风险确认。
6. 导入增强型账户后，`submitUrl` / `bid` 原样恢复，不得重新从二维码或网络推导；导入后仍只能向该钉住地址提交（S1）。
7. **移动端不提供本章的备份导出入口**：Android / iOS / 鸿蒙客户端不得实现 §14 的备份文件生成、备份文件导入、密钥文本导出、剪贴板导出或分享；`sec` 只能留在系统安全存储中。§15 的单账户二维码屏幕导出不属于备份，按 §15 执行。

### 14.6 备份与导入测试用例

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| TC-30 | JSON 备份往返：标准型 + 增强型（含 `submitUrl` / `bid` / `label`） | 账户、顺序、备注与钉住地址完整恢复；零网络请求 |
| TC-31 | 备份校验：错误 `format` / `version`、增强型缺 `submitUrl`、标准型带 `submitUrl`、非法 Base32 | 整份拒绝；不产生部分导入 |
| TC-32 | 口令加密备份：scrypt 与 PBKDF2 各一条；错误口令、篡改 `ciphertext` / `tag` / AAD | 解密成功或统一失败文案；失败时零导入 |
| TC-33 | `authenticator.txt`：otpauth 行、`account:secret`、`issuer:account:secret`、制表符 / `\|` / `;` / `,` 分隔、Base32 空格分组、注释与空行 | 合法行全部导入；非法行仅跳过并计数 |
| TC-34 | `otpauth-migration://offline?data=`：TOTP 导入、HOTP 跳过、SHA256/8 位映射、缺失 `period` 默认 30、base64 与 base64url 两种编码 | 与映射表一致；无网络请求 |
| TC-35 | 导入冲突：同 `issuer`+`account` 重复、增强型与标准型同名、文本中出现 `submitUrl` | 不静默覆盖；增强型不被降级；文本中的 `submitUrl` 被忽略 |
| TC-36 | 导出增强型密钥：二次确认、风险提示、取消导出；导出后 UI 与日志不含明文 `sec`；未开启 S18 时即时码仍不可见 | 取消时无文件；确认后按所选加密方式导出；S15 仍满足 |

## 15. 单账户二维码导出与即时码显示开关

本章定义两项**客户端展示能力**，均不改动服务端接口、登录二维码字段或备份 schema：

- **§15.2 单账户 `otpauth://` 二维码导出**：全端可用，屏幕一次性展示，不是备份文件导出。
- **§15.3 扫码型账户即时码显示开关**：默认关闭，用户显式开启后才显示即时码。

> 与 §14 的区别：§14 是**浏览器扩展**的账户备份 / 迁移文件；本章的二维码导出是**屏幕展示**，不生成文件、不支持导入、不进入备份链路。移动端可以使用本章能力，但仍不得使用 §14 的导入导出。

### 15.1 适用范围与边界

1. 两项能力对标准型与增强型账户均适用；增强型账户导出二维码时必须二次确认（§15.2）。
2. 二维码导出**不是**备份：不得生成文件、不得写入下载目录、不得进入剪贴板、不得提供“复制密钥 / 复制链接”入口。
3. 即时码显示开关**不是**新的提交入口：开启后只影响展示与复制，扫码提交路径、候选匹配和提交目标保持不变（S1、§6.2）。
4. 开关状态与二维码内容均不进入 §14 备份，不上送服务端，不参与跨设备迁移。
5. 本章不新增服务端 API、登录/绑定二维码字段或账户数据字段；`spec/openapi.yaml`、`spec/schemas/` 无需变更。

### 15.2 单账户 otpauth 二维码导出

#### 15.2.1 URI 生成

统一使用 Key URI 格式：

```text
otpauth://totp/{label}?secret={secret}[&issuer={issuer}][&algorithm={algorithm}][&digits={digits}][&period={period}]
```

生成规则：

| 组成部分 | 规则 |
| --- | --- |
| `label` | `encode(issuer) + ":" + encode(account)`；`:` 为字面分隔符。`issuer` 为空时 `label = encode(account)` 且省略 `issuer` 参数 |
| `encode()` | 对 UTF-8 字节做 RFC 3986 百分号编码；仅保留 `A-Z a-z 0-9 - . _ ~`，空格编码为 `%20`（不得用 `+`）；`:`、`@` 等一律编码 |
| `secret` | Base32 大写、无 `=` 填充、无空格；字符本身无需再编码 |
| `issuer` | 与 `label` 中的 issuer 使用同一编码结果；非空时必须同时出现在 `label` 与 `issuer` 参数中且值一致 |
| `algorithm` | `SHA1` 时省略；`SHA256` / `SHA512` 时写大写枚举 |
| `digits` | `6` 时省略；`8` 时写出 |
| `period` | `30` 时省略；其他值写十进制秒数 |
| 参数顺序 | 固定为 `secret`、`issuer`、`algorithm`、`digits`、`period`，便于逐字节比对 |
| 长度 | 完整 URI 不得超过 2048 字符；超长时拒绝导出，不得截断 |

说明：

- 增强型账户的 `submitUrl` / `bid` **不能**写入 Key URI；导出后该条目在扫码端只是一条标准 TOTP 账户，不再具备地址比对保护。
- 二维码内容只包含上述 URI，不得附加自定义查询参数、备注 `label`、账户 ID 或任何跟踪信息。

#### 15.2.2 展示与清理

1. **打开前本地认证**：每次进入二维码页面前都必须完成设备本地认证（生物识别 / 设备口令）；认证失败或取消 → 不生成二维码、不显示任何密钥信息。
2. **仅内存生成**：认证通过后才在内存中拼接 URI 并渲染二维码；不得落盘、不得写入剪贴板、不得写入日志 / 崩溃报告 / 分析事件、不得发起网络请求。
3. **默认遮罩**：打开后先显示遮罩，用户点击“显示二维码”后才渲染；不得默认直接展示可扫描二维码。
4. **60 秒强制关闭**：从首次显示二维码开始计时 60 秒；到时立即关闭页面并清空 URI 字符串、二维码位图与相关缓存。手动关闭时同样立即清空。
5. **禁止复制/保存入口**：不提供“复制密钥”“复制链接”“保存图片”“分享”按钮；平台允许时应禁用二维码图片的长按保存与拖拽。用户自行截屏不属于 App 提供的能力。
6. **截屏与任务切换防护**：
   - Android：对二维码页面窗口设置 `FLAG_SECURE`，阻止系统截图与最近任务预览。
   - 鸿蒙：开启窗口隐私模式（隐私窗口 / 防截屏），阻止截图与录屏。
   - iOS：系统不提供阻止截图的能力，必须用遮罩 + 短时展示降低暴露，并在页面显著位置说明“iOS 无法阻止系统截图或录屏，请勿在截图、录屏或共享屏幕时展示此二维码”；进入后台时用遮罩覆盖，避免任务切换快照泄露。
7. **重新打开需重新认证**：关闭（手动或超时）后再次打开，必须重新执行本地认证，不得复用上一次的 URI 或二维码位图。

#### 15.2.3 增强型账户的二次确认

1. 增强型账户在本地认证通过后，还必须展示二次确认；**标准型账户只需本地认证**。
2. 二次确认文案必须包含：

   > 导出后该账户的防钓鱼优势失效，任何扫码者都能独立生成动态码。

3. 用户在二次确认中取消 → 不生成、不显示二维码，返回账户页。
4. 确认后才按 §15.2.1 生成二维码；展示与清理规则与标准型相同。
5. 二次确认不得被“记住选择”跳过；每次导出增强型账户都必须确认。

### 15.3 扫码型账户即时码显示开关

1. **默认关闭**：全新安装、首次登录、导入备份或迁移到新设备后，开关必须为关闭状态。
2. **开启条件**：必须先完成本地认证（生物识别 / 设备口令），并勾选风险确认（例如“我了解开启后动态码可能被截屏、录屏或恶意应用获取”），两项都完成才可开启。
3. **开启后的行为**：
   - 扫码型账户详情页显示当前时间步的即时码与倒计时；
   - 允许复制即时码；
   - 提交路径、候选匹配（§6.2）与提交目标（S1）完全不变，仍然只能通过扫码向钉住地址提交；
   - 即时码仍不得导出为文件、分享或写入日志。
4. **关闭后的行为**：立即隐藏即时码与倒计时，清空界面值、内存缓存与任何已渲染的码；不主动读取或清空系统剪贴板。重新开启必须再次通过本地认证与风险确认。
5. **开关状态存储**：仅存本地设备设置，随设备保存；**不得**写入 §14 备份、不得随备份/迁移恢复、不得上送服务端、不得写入日志或分析事件。
6. **SDK 约束**：开关关闭时，SDK 不得向调用方返回即时码；开关开启时，仅允许受信任的已认证 UI 获取当前显示值，仍不得提供常驻的公共 `getCode()` API。
7. **与 S15 的关系**：S15 的“默认不显示”仍然成立；S18 只是用户显式接受风险后的例外。两者不冲突，也不改变 S15 对导出 / 分享即时码的禁止。

### 15.4 字段与 API 变更

- 服务端：**无变更**。不新增接口，不新增请求/响应字段，登录与绑定二维码格式不变。
- 备份：**无变更**。§14 的 JSON schema 不增加开关字段或二维码字段；即时码开关不进入备份。
- 账户模型：**无变更**。开关是设备级本地设置，不写入单个账户记录。
- 客户端：新增二维码展示页面、本地认证调用、60 秒计时与清理逻辑、S18 开关与风险确认流程。
